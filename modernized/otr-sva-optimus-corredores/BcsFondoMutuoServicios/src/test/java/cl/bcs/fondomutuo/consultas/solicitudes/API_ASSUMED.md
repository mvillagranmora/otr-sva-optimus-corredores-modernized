# API assumed by the FMM-SFM tests (ConsultarSolicitudesFFMM and ConsultarSolicitudesFFMMWS, F3 W1 front 3)

The production code does NOT exist yet. The tests of this package (`CasoSfm`, `SujetoSfm`, `SfmEquivalenciaTest`, `SfmDeterminismoTest`, `SfmReglasTest`,
`SfmCompuertaTest`) are written against EXACTLY the classes, constructors and methods below, all in package `cl.bcs.fondomutuo.consultas.solicitudes` (main source set)
unless another package is named. Legacy FQNs: `cl.bcs.fondomutuo.ConsultarSolicitudesFFMM` and `cl.bcs.fondomutuo.ConsultarSolicitudesFFMMWS` (one handler each). Design = F1/F2/FSA
style: service + read port + JavaCall handler, closed by default, read only, so **no lock, no Tesoreria, no custody, no sequences, no write port, no G1..G5 gate, no collaborator
outside the module** (the two classes read only the view `FMM.ConsultarSolicitudesFFMM`, `FMM.TipoMovimientoFondoMutuo`, the WS also `TES.IngresoEgreso` / `TES.ComprobanteDetalleOrigen` /
`TES.ComprobanteDetalle`, and two parameters). If production needs another shape, change the tests (not the golden): nothing of the comparison depends on these names except the
entry points marked (*).

## 2. Contract types (field names = legacy, JSON = legacy)

* `Entrada`: `Long p_IdEmpresa; Long p_IdUsuario; String p_IdModulo; Long p_IdCliente = 0L; String p_TipoSolicitud = ""; p_Origen = ""; p_Folio = ""; p_TipoAhorro = ""; p_TipoCuenta = ""; p_IdSerieFondo = ""; p_Estado = ""; p_FechaDesde = ""; p_FechaHasta = ""` (the legacy constructor defaults when the key is absent; an explicit JSON `null` stays null and the service raises `NullPointerException`: SFM-C08). `p_IdUsuario` and `p_IdModulo` are received and never read.
* `Salida`: `Long P_OUT_ERRORESCONTADOR = 0L; List<kit.MensajeSalida> P_OUT_MENSAJES = []; List<Solicitud> P_OUT_SOLICITUDES = []` in this field order. The counter and the messages are NEVER filled (no validation of basic requirements or profile).
* `Solicitud` (SFM, 74 declared fields, 73 written): the fields of the legacy `ConsultarSolicitudesFFMM.Solicitud` in the SAME DECLARATION ORDER (`IdCliente, TipoSolicitud, FechaConsulta, Origen, NumSolicitud, DetSolicitud, Estado, EstadoDetalle, Rellamada, ..., IdSerieFondoOrigen, ..., IdSerieFondo, IdContrato, FechaFinalReinversion`), with the legacy Java types (`Long`, `String`, `BigDecimal`; every date and hour of the view is a `String`); the four `MontoCuotasComprometidas / MontoCuotasDisponibles / MontoPesosComprometidos / MontoPesosDisponibles` start as `BigDecimal.ZERO` (scale 0: the golden shows `0` when nothing is added and `0E-8` when a zero of scale 8 is added).
* `WS Solicitud`: the same fields, then `Long IdComprobante` and `java.sql.Timestamp FechaIngresoLocal` AT THE END, in ONE class (Gson writes the fields of a subclass BEFORE those of its superclass: `extends` would change the output order and the golden compares the text). `Salida.P_OUT_SOLICITUDES` is a list of it.
* JSON in and out: **a new `com.google.gson.Gson()` PER CALL** (the plain Gson of the legacy; NOT the static `JsonLegacy.plano()` and NOT the `Utils.getGsonBuilder()` of FSA): the default date format of Gson (`MMM d, yyyy, h:mm:ss a`, with the JDK 20+ narrow no-break space U+202F, for `FechaIngresoLocal`) takes the zone of the JVM when the Gson is CREATED; a cached instance would freeze it (the same remark `JsonFsa` makes). Null keys are not written; `BigDecimal` is written with its `toString` (`0E-8`, `1E-8`).

## 3. Behaviour the tests pin (bug for bug; the golden is the oracle, this is the index)

* **Order of reads** (FM-SFM-02/03): the two parameters `PLATAFORMA/PLA.FiltroAdministracionCarteraWS` and `FONDOMUTUO/WS_SOLICITUDES_MUESTRA_SOLO_SOLICITUDES_NO_AUTOMATICAS` first (a missing one is the plain `Exception("Parametro X en modulo Y no encontrado")`; the kit raises its `ParametroNoEncontradoException` with the same text), THEN the nine `esFiltro` calls in the order cliente, tipo, origen, folio, ahorro, cuenta, serie, desde, hasta (a null field => `NullPointerException`), THEN `PLA.SegundosZonaHoraria` (`Long.parseLong` => `NumberFormatException`; cast `(int)`: 3000000000 becomes -1294967296; the WS reads it and does not use it), THEN the SQL. `p_Estado` is NOT a SQL parameter: it is checked in memory after the state calculation (`null` => `NullPointerException` at the end).
* **Filters** (FM-SFM-02): `FiltraX = S` iff the text is not empty (no trim) / the client is not 0; `FiltraTipoMovimiento = S` always; ADC (`EsADC = 'N'`) only when the parameter equals `"S"` exactly; not-automatic (`IngresoAutomatico = 'N'`) only when the parameter equals `"S"` exactly; dates compared as TEXT.
* **Hour and entry date** (FM-SFM-03 / FM-SFM-07): SFM: `HoraSolicitud := LocalTime.parse(hora, "HH:mm:ss").plusSeconds(offset).format("HH:mm:ss")` (wraps at midnight; the date is NOT adjusted), `FechaIngreso := FechaSolicitud + " " + HoraSolicitud` (`NullPointerException` for a null hour or date, `DateTimeParseException` for a text that is not `HH:mm:ss`). WS: `FechaIngreso := FechaIngresoLocal.format("yyyy-MM-dd HH:mm:ss")`, `FechaSolicitud := FechaIngresoLocal.toLocalDate().toString()`, `HoraSolicitud := FechaIngresoLocal.toLocalTime().toString()` (ISO: `09:05` when the seconds are 0, `09:05:00.500` with a fraction); a null `FechaIngresoLocal` => `NullPointerException`.
* **Global state** (FM-SFM-04, D-F3A-08): rows of type `"REV"` (exact) are grouped with the REV rows by (`FolioRelacionado != 0` and equal) OR equal `NumSolicitud`; every other row with the non-REV rows by (`FolioContrato != 0` and equal) OR equal `NumSolicitud` (`Long.equals`: a null key => `NullPointerException`, as in the legacy). The state is `""`, then ANULADO if all are ANULADO, INGRESADO if all INGRESADO, TERMINADO if all TERMINADO, EN PROCESO if any is EN PROCESO (the last that holds wins). Without `p_Estado` the rows with `""` are DROPPED; with it `equals`.
* **Amounts** (FM-SFM-05): per group, `DECIMAL128` additions: a row whose `EstadoDetalle` is neither TERMINADO nor ANULADO (null and unknown included) adds to "comprometidas", TERMINADO to "disponibles", ANULADO to none; REV adds `MontoCuotasDestino`/`MontoPesosDestino`, the others `MontoCuotasOrigen`/`MontoPesosOrigen` (a null addend => `NullPointerException`). Every row receives the totals of its group.
* **Output order** (FM-SFM-06): the order of the SQL result (no `ORDER BY`), preserved through every step. The legacy ran on `parallelStream()`; the new code may be sequential, but the equivalence and determinism tests (N = 20) require the same list.
* **D-F3A-28 (the only HANA-vs-H2 point the golden decides)**: the SQL selects `"IdSerieFondo" as "IdSerieFondoOrigen"`; the legacy `SQL.queryParallel` (`RowSetDynaClass`) fills the pojo by the underlying column NAME on H2, so the golden has `IdSerieFondo = <view value>` and `IdSerieFondoOrigen` ABSENT (null). `SqlNombrado.consultar` maps by LABEL and would give the opposite: the adapter needs a by-name variant. Whether the HANA driver reports the alias or the base name is NOT verified (Q-F3A-3): two cases pin it (`serie-origen-alias-queryparallel`, `ws-...`); re-evaluate them if the owner confirms HANA behaves differently.
* **Exceptions**: class compared (the message only for a plain `Exception`, i.e. the missing parameters). KNOWN KIT DEVIATION **DESVIO-KIT-1**: for a null or unknown company (`empresa-nula`, `empresa-sin-configuracion`, `empresa-ausente`) the legacy raises a `NullPointerException` out of `ConfiguracionSistema`; the module's kit documents that it raises `ParametroNoEncontradoException` instead. The harness accepts either class for those three slugs ONLY (`CasoSfm.DESVIO_KIT_EMPRESA_SIN_CONFIGURACION`) and asserts the kit message; every other case must match the class exactly. To be approved by the owner (and the kit changed or the deviation registered).
* Read only: the tables of the dump come back unchanged; no session-local table, no autonomous commit, no sequence, no collaborator call.
