## B2. The JDBC contract of a Postgres procedure call (`ProcedimientosPostgres.llamar(con, hanaName, in)`)

1. **Selection.** `hanaName` must be one of the 8 rows of the resource. Anything else (another HANA procedure, a Postgres name, wrong case, spaces, empty, null) throws `UnsupportedOperationException` (503 by `GlobalExceptionHandler`) whose message names it, with ZERO calls on the connection. A `NO_DISPONIBLE` one throws `ObjetoNoDisponibleException` (message names the HANA procedure), also with zero calls.
2. **Procedures (7).** `con.prepareCall("{call <pg name>(?,?,...)}")`: JDBC escape form, one `?` per parameter, OUT and INOUT included, in the order of the Postgres signature (layout free). No `CALL` raw text, no named parameters.
3. **IN parameters.** Bound at their position by key, ignoring case and underscores (`p_IdEmpresa`, `P_IDEMPRESA`, `p_id_empresa`, `p_idempresa` are the same key; unknown keys are ignored). `bigint`: a JSON number or numeric text bound as a number (`setLong`); not a number: `IllegalArgumentException` before anything is executed. `character varying`: a JSON number or text bound as text. Absent or JSON null: `setNull(i, Types.BIGINT)` / `setNull(i, Types.VARCHAR)`; the exception is `p_aplica_origen_evento`, absent or null is bound as `""` (the legacy passes `''` and the Postgres default is `''`).
4. **OUT parameters.** `registerOutParameter(i, Types.VARCHAR)` for `character varying`, `Types.INTEGER` for `integer`. An OUT parameter is never bound as a value.
5. **INOUT refcursor** (`p_out_advertencias_detalle`, `p_out_errores_detalle`, `p_out_id_evento`): `setNull(i, Types.OTHER)` AND `registerOutParameter(i, Types.OTHER)`. After `execute()` the value is read with `getObject(i)`; a `ResultSet` is read to the end (labels as the cursor gives them, values as text) and CLOSED; `null` means an empty array.
6. **Execution and reads.** One `execute()`. OUT values are read BY INDEX after it (reading by name is refused by the fake as pgjdbc refuses it). A scalar OUT is the JSON text of the value under its legacy name (`"0"` for the integer 0, JSON null for NULL); a cursor is a JSON array of row objects.
7. **Answer.** Only the OUT / INOUT values, each under its legacy name (A2-5). No IN is echoed and no snake_case key is left. The input `JsonObject` is not modified.
8. **Function (`ConsultarFormatos`).** `con.prepareStatement("SELECT * FROM fn_pla_consultar_formatos()")` (no `CALL`, no OUT parameter, nothing bound), `executeQuery()`; the answer is `{"P_OUT_MONEDAFORMATO": [rows]}`, each row with the 18 HANA labels (PascalCase of the column) and TEXT values (`getString`, as every HANA result set value was), JSON null for NULL; no rows is `[]`.
9. **Resources.** The statement and every result set are closed on every path (success, SQL error). The connection is never committed, rolled back, closed or switched out of its auto-commit mode: the caller owns the transaction (T-13, and a cursor needs it). A `SQLException` of `prepareCall`, `execute` or a read reaches the caller as the SAME exception object.
10. **No state.** Every call prepares its own statement; nothing is kept between calls.

## C2. `EVT.AgregarEvento`: four arrays of composite types

HANA received four local temporary tables filled with the JSON rows. Postgres gets four arrays (`p_eventos`, `p_valores`, `p_archivos_adjuntos`, `p_id_direcciones`, positions 4 to 7):

- `con.createArrayOf("<type>", Object[] rows)` with the UNQUALIFIED type name (`ty_pla_evt_agregar_evento_eventos`, `..._valores`, `..._archivos_adjuntos`, `..._id_direcciones`), one `String` per row, bound with `setArray(i, array)`. Four arrays are always created, empty ones included (`[]`, JSON null, not an array and absent are all an EMPTY array, not NULL: HANA created an empty table).
- The `String` of a row is the record literal of the composite: `(f1,f2,...)`, attributes in the order of the type (not of the JSON keys); a JSON key is found ignoring case and underscores; a missing key or JSON null is an empty field; a field is double-quoted when it is empty text or contains a comma, parenthesis, double quote, backslash or whitespace, and inside quotes `"` and `\` are doubled; non-ASCII letters and other punctuation are not quoted. Numbers are their JSON text.
- `bytea` (`archivo_adjunto`): the JSON text is base64; the field is `\x` plus lower-case hex (so, quoted: `"\\x0aff"`).
- `timestamp(0)` (`fecha_creacion_sistema`): passed through as given (a date, `date time`, ISO with `T`), no conversion.
- An element of a table parameter that is not a JSON object fails with a `RuntimeException` before anything is executed.
- Example (the login's real event): `(SOLICITUD_CAMBIO_CLAVE,0,2026-11-03,0,777,0)`, `(0,Nombre,"Juan Perez")`, `(0,5551,TO)`.

## Open questions (Q-LOGINPG2-n), each with a recommendation. To be settled by a READ-ONLY execution in T-36.

- **Q-LOGINPG2-1 `registerOutParameter` on a procedure call.** The tests pin `prepareCall("{call p(?,...)}")` plus `registerOutParameter`. pgjdbc (42.7.x) only accepts `registerOutParameter` on a statement it treats as a function call, and for a PROCEDURE it depends on `escapeSyntaxCallMode`: `select` (default for `callIfNoReturn` when an OUT is registered) emits `SELECT * FROM p(...)`, which fails for a procedure ("p is a procedure"); `call` emits `CALL p(...)`. Assumption: the datasource must carry `escapeSyntaxCallMode=call` (or `callIfNoReturn` verified), a connection property (`SPRING_DATASOURCE_URL` or `spring.datasource.hikari.data-source-properties`). Recommendation: T-36 runs ONE procedure with OUT only (`sp_pla_obtener_fechas`, a pure read) with each mode and records the text pgjdbc sends. If `registerOutParameter` is refused with `call`, fall back to `prepareStatement("CALL p(?,?,?)")` with `setNull` on the OUT positions and read the single result row by column label (the OUT parameter names): the tests that bind and read by index would change in `JdbcGrabador` and in the contract (B2-2, B2-4, B2-6) only.
- **Q-LOGINPG2-2 HANA names of view columns and of OUT parameters.** The xlsx has no view columns and the saved HANA catalog has no columns or parameters. The HANA name of a view column is DERIVED (PascalCase of the snake_case); the derivation reproduces every column the HANA SQL cites (23 by name, plus the ten POJO fields of `SQL_ACCESOS`); the other 125 rows of the view-column CSV are unverified. The legacy OUT names follow the rule A2-5; only the ones the login reads are verified by reading its source. `P_STATUSCODE` and `P_OUT_IDEVENTO` are guesses nothing reads. Recommendation: T-36, read-only, `SYS.VIEW_COLUMNS` and `SYS.PROCEDURE_PARAMETERS` of HANA QA, compare with the CSV and the resource; no query of data.
- **Q-LOGINPG2-3 Refcursor read.** Assumed: `getObject(i)` on a registered INOUT refcursor returns a `ResultSet` (pgjdbc fetches the portal) and needs a transaction (the login connection runs with auto-commit off). Registering with `Types.OTHER` follows the pgjdbc documentation for cursors; `Types.REF_CURSOR` is not assumed. The columns of the two error cursors are not in the signatures: labels are passed through as the cursor gives them; the login code reads only the counters. Recommendation: T-36 opens one of the error cursors on a read-only user and records the labels.
- **Q-LOGINPG2-4 Composite arrays.** Assumed: `createArrayOf(typeName, String[])` with the text form of the record is accepted by pgjdbc for a composite array type and the server parses each element. pgjdbc may instead want `PGobject` elements or `Struct`. Recommendation: T-36 builds ONE array with one row and calls the procedure inside a transaction that is rolled back (it writes nothing if rolled back; still needs approval) or, read-only, runs `SELECT ?::ty_pla_evt_agregar_evento_valores[]` with the same array and reads it back. If `String` elements are refused, change the element class in `ApiLoginPg2`/`JdbcGrabador` only.
- **Q-LOGINPG2-5 Qualified or unqualified type name.** The catalog prints `bscl.ty_...[]` in one file and `ty_...[]` in the other. Pinned unqualified (flat names, the schema comes from `currentSchema` in the URL). If the deployment does not set the search path the tests change to `bscl.` in one constant.
- **Q-LOGINPG2-6 NULL ordering of `SQL_ACCESOS`.** HANA sorts NULL first in an ascending ORDER BY, Postgres last. The Postgres text is pinned with `ORDER BY padre NULLS FIRST, orden NULLS FIRST` and a fixture row with NULL `padre`/`orden` shows the difference. If the real view never has NULLs there, the clause is harmless.
- **Q-LOGINPG2-7 `SELECT *` of `SQL_ACCESOS`.** The Postgres text lists the ten fields of the POJO (`UsuarioAcceso`); the view has 17 columns (the other seven are not read by the code). Recommendation: keep the explicit list; if a field is added to the POJO the list and the test change together.
- **Q-LOGINPG2-8 Generic `/call` path.** The generic dispatchers keep answering 503 in Postgres mode for every name, the eight included, because they are out of scope of the plan (TODO_MVP 10.1). The login does not use that path for them. If the owner wants `/call` to serve the eight in Postgres, the dispatcher can delegate to the selector for those names; no test pins either answer for the eight names on the dispatcher except that the data source is not used for any OTHER name.
- **Q-LOGINPG2-9 Time-stamp and bigint binding types.** `setLong` for `bigint` and `setString` for `character varying` are assumed enough (the server infers the unknown types of a `CALL`). Recommendation: T-36 confirms with `CALL` on the read-only functions.
- **Q-LOGINPG2-10 What round 2 cannot show.** The text of the six statements was checked on H2 MODE=PostgreSQL and against the catalog oracle, not on Postgres; the Parse/Describe check of round 1 (`ValidaSqlPg.java`, no execution) should be repeated for them before T-36. Types of the Postgres stand-ins are assumed equal to the HANA ones.
