# APV family B (traspasos): characterization tests, APV-B-01 .. APV-B-368 (240 cases: 199 + 41 added for the recaudacion success paths and the mixed retention list)

The expected values are RECORDED by executing the unmodified legacy classes (`legacy/otr-sva-optimus-corredores/BSCL/APV/JAVA/BcsAPVServicios/src/cl/bcs/APV/...`) on H2
(`MODE=LEGACY`) with scripted collaborators; nothing is computed by the tests and the legacy source is never edited. BUSINESS_RULES.md has no rule of this module, so the
behaviour ids are `APV-B-NN` (not `RULE-NNN`); every test method name starts with its id (`apvB101_...`) and a comment above it cites the legacy `file:line` it pins.

## What a test runs

`legacy JSON -> adapter -> REAL use case (cl.bcs.apv.application.traspasos.*Servicio) on H2 -> adapter -> legacy JSON`, in process, through
`cl.bcs.apv.support.ApvPipelineDeCaso.crear(jdbc, cfg, dic, col, sec, reloj, archivos).invocar("cl.bcs.APV.<Clase>", json)` (CONTRATO.md section 3). Each case then compares
(`support/Verifica`, every facet a soft assertion, so a red test lists everything that differs):

1. the output JSON (canonical: key order free, nulls dropped, numbers by value) or, when the legacy threw, the exception SIMPLE CLASS NAME (the message is recorded for humans only);
2. the table dumps the case declares (`"tablas"`), taken after the transaction ends (commit on return, rollback on throw: the production handler model);
3. the collaborator trace: every call to a service OUTSIDE the APV module (service name + the JSON the legacy handed it), in order;
4. the sequences requested (legacy `Utils.getSecuencia(name, n)` is recorded as `name#n` and expanded to `n` requests of `name`: the modern port gives one value per call).

Collaborators that are OTHER APV classes (`ValidaContratoSAAPV`, `CambiarEstadoContratosSAAPV`, `ModificarPortafolioTraspaso`, `IngresoRecaudacionTraspaso`,
`GrabarRecaudacionTraspaso`, and what they call) run FOR REAL in the oracle and are typed use cases in the modern code; they are never scripted. Collaborators outside APV
(Socio de Negocio, Plataforma, Tesoreria, Cuenta Inversion, stored procedures) are scripted doubles answering what `case.json "colaboradores"` says, on BOTH sides (oracle fake and
`support/ColaboradoresDeCaso`).

## Layout

- Cases: `src/test/resources/apv-b/cases/APV-B-NN_<slug>/{case.json, seed.sql, expected.json}` (directory names stay under 70 characters: Windows MAX_PATH).
- Oracle: `src/test/resources/apv-b/legacy-oracle/{record.sh, mutation-check.sh, runner/OracleRunner.java, shims/, tools/{gen_shims.py,mkschema_ext.py}}`; schema `schema-apv-b.sql` (the original family B
  objects) + `schema-apv-b-ext.sql` (GENERATED by `tools/mkschema_ext.py` from `schema-apv-b.sql` and, read only, family C's `apv-c/schema-apv-c.sql`: the recaudacion objects), `seed/{base.sql,config.json}`,
  `h2-dialect/` (no override needed so far), `hana-sql/` (byte-identical copies of statements an override replaces; empty).
- Tests: this package, one class per legacy class (`<Clase>Test`), plus `FamiliaBSelfCheckTest`. Support: `support/` (Caso, Verifica, Equivalencia, Canon, Dump, H2Hana, doubles).
- Dual-execution hook: `-Dequivalence.out=<dir>` through `cl.bcs.apv.support.VolcadoEquivalencia` (family `familia_b`; created by the family A agent, reused unchanged).

## Re-record, add a case, mutation check

1. Add the case in `cases/APV-B-NNN_<slug>/`: `case.json` = `{servicio (class under cl.bcs.APV), entrada (the legacy JSON), config {"MODULO/Parametro": value | null removes}, colaboradores,
   secuencias {name: firstValue}, enmascarar ["Key"], sinOrden ["Key"], tablas [{nombre, orden, columnas, excluir, expresiones, enmascarar}]}` and `seed.sql` (H2 statements over `schema-apv-b.sql`).
   `colaboradores.<Servicio>` is `{"salida": {...}}` (every call), `{"salidas": [{...}, ...]}` (k-th call, the last repeats) or `{"lanza": "text"}`; the output JSON must list EVERY field the legacy
   class serialises (the oracle refuses an incomplete script: `Hooks.salida`). Stored procedures: `"StoredProcedure": {"<procedure name>": {"salidas": [...]}}` with the OUT parameters by name
   (scalars as values, table parameters as arrays). `AgregarLog` and `CrearEventoAutorizacionMasivo` answer "nothing to report" when not scripted (same table in `Hooks` and `ColaboradoresDeCaso`).
2. `legacy-oracle/record.sh APV-B-NNN` (JDK 25, jars in `~/.m2`; `LEGACY_BSCL` / `LEGACY_APV_SRC` point at another legacy copy, `ORACLE_WORK` at a SHORT scratch path, `ORACLE_REUSE_CLASSES=1` skips
   the compilation when only cases changed; a prefix like `APV-B-2` matches 2, 20-29, 200-249). Two full re-recordings of the recorded cases are byte-identical (checked).
3. Add the id to the `CASOS` list and one `apvBNNN_` method of the test class with the cited `file:line`; review the golden by hand.
4. `legacy-oracle/mutation-check.sh <file under cl/bcs/APV> <line> <text> <replacement> [casePrefix]` copies the legacy sources and the resources to a scratch directory, applies the one-line mutation
   there, re-records and lists the goldens that changed (nothing in legacy/ or in the module is touched).

## Legacy defects for SME review (kept and pinned as legacy behaviour)

Findings that make a class (almost) unusable in the repository snapshot, in decreasing weight:

- **CrearTraspaso, GrabarContratoTraspasoSAAPV (and anything else calling `Traspaso_Insert.sql` / `ContratoSAAPV_Insert.sql` with these POJOs)**: the INSERT statements bind
  `:FechaSuscripcion` / `:CierreSolicitud` (traspaso) and `:Canal` (contrato) but the Java classes have no such field, so `SQL.batch` throws `SQLException("Map Object failed <field> Query: ...")`:
  CrearTraspaso answers an ERROR message whose text is that SQL layer message (cases 15-16); GrabarContratoTraspasoSAAPV throws for EVERY row that reaches the contract insert (INGRESO or EGRESO), so
  nothing is ever written and its observable behaviour is the collaborator trace before the exception (cases 214-234).
- **CalculoMontosDesinversion**: `ObtenerDetalleTraspasoDesinversion.sql` does not select `UFTraspaso`, so the "by UF" branch can never run (129); the ROUND_UP / ROUND_DOWN / ROUND_HALF_UP indicators never set
  `MontoADesinvertirCLP`, so they all end in a caught NullPointerException (114-116, 126) and only HALF_DOWN produces a result; a percentage below 1 (e.g. 0.5) is treated as "amount mode" (`longValue()==0`, 121);
  total >= patrimony reports `P_OUT_MONTO_TOTAL` 0; every error message has type CALCULO, so `P_OUT_ERRORESCONTADOR` is 0 even when the calculation failed; `P_OUT_PORCENTAJE` comes from a double division
  (`new BigDecimal(double)`: the exact binary expansion is part of the golden).
- **CalculoRetencionTraspasos / CrearTraspasoTesoreria**: the retention regime is compared with the portafolio's `IdMatrizAgrupadorAPV` (CalculoRetencion 41-42) or, in CrearTraspasoTesoreria, with `==` between two
  `Long` objects (works only for ids inside the Long cache, <= 127: cases 164-165); two matching retention rows are applied one after the other and only the last retention is reported (44);
  the error branch sets no message type, so the counter stays 0 (51).
- **GrabarRecaudacionTraspaso (success and failure paths, 300-316)**: the caller never reads the messages of `CrearRecaudacionDeposito`, only `P_OUT_IDREC`: a Tesoreria ERROR for the deposit movement is ignored and the flow
  goes on as a success (303), and every early return of the deposit service (no PAC cash box, company without default portafolio, corredora account not found) leaves `P_OUT_IDREC` null and the unboxing in the caller throws
  NullPointerException (304-306); a reconciliation that does not match is reported as a message typed OK with code `ERROR` and counter 0 (307, 322, 327, 343); one `MensajeSalida` instance is reused, so a Tesoreria error in
  the DIS step OVERWRITES the already added `CONCILIADO_OK` message with `ERROR_RECAUDACION_CLIENTE` (308, 313); the `ERROR_RECAUDACION_CLIENTE` branch after `CrearRecaudacionCliente` is unreachable (its messages are typed APV,
  counter 0); the traspaso/contract lists are built with reference comparisons (`!=` on String and Long), and with several rows the contract of the LAST row is assigned to every client (314); a failed traspaso update does not
  try the contract update (309) while a failed contract update leaves the traspaso already COM (310).
- **IngresoRecaudacionTraspaso (320-329)**: for type I the deposit amount is the SUM of `MontoPesoDetalle` of the view, not the `MontoTraspaso` of the input (322); with more than one traspaso a failure rolls back EVERYTHING
  (including the traspasos that succeeded, 326) and only the error rows plus the REC result of the last traspaso are answered; the two spot work tables are emptied only when the first has rows (328-329).
- **ReaperturarTraspaso (340-344)**: a recaudacion that does not reconcile is answered as `REAPERTURAR_TRASPASO_OK` plus the not-matching row, no error counted (343); a Tesoreria failure in the DIS step leaves the new detail, the
  portafolio-contract relation, the deposit and the clients written (344); the detail with `MontoReapertura` 0 is skipped (342). Observed with the seeded views: the recaudacion ends DIS (funds distributed, solicitud FFMM
  created) with one reapertura detail (340) and stays CON with two (341); the cause (the RECTRA validation walks the detail view rows by position, ValidaContratoSAAPV.java:455-485) was not investigated further.
- **CrearTraspasoTesoreria with several retentions (361-368)**: every matching retention is applied one after the other to the SAME order amount (15% then 10% of the remainder: 765000), but only the LAST retention amount
  (85000) is reported in the `EGRRET` pair, so the movements do not add up (362); a retention with a regimen id outside the Long cache never reaches an order (363); the movement numbers run across RV and FFMM orders and
  across traspasos (368).
- **IngresoRecaudacionTraspaso (guards, 235-242)**: `tipoTraspaso == "I"` and `IdEstado != "COM"` compare Strings by reference, so the validation never rejects anything for a value that came from JSON and
  `ERROR_TRASPASO_RECAUDACION` is unreachable (238); two rows of the view with the same traspaso make `Collectors.toMap` throw (239).
- **CambiarEstadoTraspaso**: the traspaso list grows and is batched whole for every row; `result[0]` is the FIRST row's result, so a missing traspaso after a good one answers OK and the reverse answers ADVERTENCIA (10-11);
  a failed row makes every later row fail (12); a null `IdTraspaso` makes the error branch itself throw (14).
- **ModificarOrigenDestino**: one `MensajeSalida` instance is reused for every row, so the messages of a batch all show the LAST row's result (3-4); the counter is never set when there are no rows (5).
- **CrearOrdenTraspaso**: every message carries the FIRST id of the sequence block while the rows take their ids from the database sequence (18).
- **TraspasoCuentasBancarias**: `llenadoTransicionArmada` fills `IdTipoCuentaBancariaSocio` from the bank account type (160); `p_IngresoEgreso`/`p_FormaDePago` ARE filled but `CrearTraspasoTesoreria` never fills its output lists;
  the index of an `IdComprobante` result is used on the movement list (155).
- **ModificarPortafolioTraspaso**: a detail with `EsReapertura S` is always treated as new (204); `SalidaCliente.P_OUT_REFIDPORTAFOLIO` is shared by all rows (id carry-over); the `ValidaContratoSAAPV` call with option M
  runs an UPDATE with a null folio (no effect).
- **GrabarTraspasos**: the "port INA is reactivated" branch is reachable only when the stored procedure returns an existing id (188), because `ValidaContratoSAAPV` excludes INA portafolios; every message carries the last
  detalle id.
- **ReaperturarTraspaso**: stage 1 rows are saved when a later row fails (partial commit, 248).
- Null/short inputs end in raw NullPointerException / IndexOutOfBounds / StringIndexOutOfBounds in most classes (pinned by exception class name only: the JDK "helpful NPE" text names compiler locals, so it is masked).

## Not covered (NOT PROVEN) and why

Since the second delivery the success paths of `GrabarRecaudacionTraspaso`, `IngresoRecaudacionTraspaso` and `ReaperturarTraspaso` (stage 2) ARE pinned (300-344): the five family C classes
(`CrearRecaudacionDeposito`, `CrearRecaudacionCliente`, `ConciliarDeposito`, `AsignarContratoARecaudacion`, `ProcesarDistribucion` with option RECTRA) run for real in the oracle, on a schema that is the union of
family B's and family C's (read only; see Assumptions). What stays PARTIAL inside those classes, and why:

- Only the paths those three entry points reach are pinned: an INDIVIDUAL client, the RECTRA option, one deposit per call. The employer branches (`REC.Empleador`), the masivo mode of `ConciliarDeposito`, the automatic
  contract assignment search of `AsignarContratoARecaudacion`, the non-RECTRA options of `ProcesarDistribucion` (DIS with RV orders, rezago) and the FFMM request failure branches are family C's / family A's cases
  (`apv-c`: 365 cases; `apv-a`), not repeated here.
- The `ConsultarRecaudadoDistribuido`, `ConsultarGestionContratosSAAPV` and `ConsultarDetalleTraspasosAPV` HANA views are seeded rows, not derived from the tables (the DDL is not in the repository): whether the real view
  returns the same rows for the same table state is not proven. The reapertura distribution result (340 DIS vs 341 CON) depends on those view rows.
- `GrabarRecaudacionTraspaso` was not driven with an employer (`IdEmpleador != 0`; the field only reaches the contract list and the SQL ignores it), nor with a bank other than the corredora's account.
- Concurrency of the sequence blocks (`IdRecaudacion` requested per call): the oracle gives consecutive values, HANA may not.
- `ValidaContratoSAAPV` and `CambiarEstadoContratosSAAPV` are NOT pinned here as direct entry points on purpose: family A already pins them (40 and 36 cases in `apv-a/cases`, plus `AsignarContratoARecaudacion`, 12);
  family B exercises them only through its callers, so a second set would duplicate them.
- Stored procedures run only as scripted collaborators (the Java side is characterised, not the HANA procedure).
- `CrearTraspasoTesoreria`: the mixed FFMM + RV list with several retentions is now pinned (360-368); orders of USD portafolios and more than two portafolios per client are not.

## Assumptions (documented)

- The HANA DDL is not in the repository: `schema-apv-b.sql` is INFERRED from the legacy SQL and POJOs (columns read or written, types as the SQL comments say, money DECIMAL(26,8)/(28,16)). Views are tables the seeds fill.
  Two types matter for behaviour: `TRA.DetalleTraspaso.FechaIngreso/FechaModificacion` are DATE (the legacy maps them to `java.util.Date`), `SCS.PortafolioContratoSAAPV.PeriodoInicio/Termino` are VARCHAR(7) (`yyyy-MM`).
- Union schema for the recaudacion paths: `schema-apv-b-ext.sql` is GENERATED by `legacy-oracle/tools/mkschema_ext.py` (family C's `schema-apv-c.sql` is only read). Tables only family C defines are copied; for a table both
  define, the columns only C has are added as INVISIBLE (not part of `SELECT *` nor of an INSERT without a column list, so the 199 earlier goldens are byte-identical: checked by re-recording them); three columns that family B
  had inferred as BIGINT but hold codes/text (`REC.Recaudacion.CuentaCorriente/IdTipoDeposito/IdEstado`) become text. VARCHAR widths are NOT aligned to family C's wider ones because some earlier goldens pin a "value too long"
  SQLException (case 12). The two spot work tables IngresoRecaudacionTraspaso empties (`SPT.CrearOperacionSpot_Proceso`, `GBL.SaldoFlujoCaja_Proceso_Paso`) have one inferred key column (only count/truncate/delete touch them).
- `seed/base.sql` now also seeds `PLA.MonedaFormato` (CLP/USD/UF, same synthetic rows as family C: the legacy `MonedaFormato` caches the table for the JVM lifetime). The recaudacion configuration keys
  (`APV/REC.LiquidacionAutomatica`, `REC.ValidacionSAAPV_*`, `PLATAFORMA/APV.AbreRegistrosTesoreria`) are per-case `config`, NOT in `seed/config.json`: case 152 pins the "parameter not found" failure of that key.
- `support/H2Hana` gained the rewrites family C needed (`CURRENT_TIMESTAMP` as the fixed clock, `TO_CHAR`, `CS_*` column attributes, UPDATE ... FROM ... JOIN as MERGE, `TO_NUMBER`, `TO_DECIMAL(x,p,s)`, format
  patterns with fractions); `Dump` gained the `"*Key"` mask (random `IdTrabajo` of the `AgregarLog` calls of `ProcesarDistribucion`: `Math.random()` in the legacy). The oracle run class path now includes the Plataforma sources
  (the legacy `MonedaFormato` reads its SQL resource from there). None of this changes the earlier goldens (checked).
- Clock: the legacy takes the date from `new Date()` / `System.currentTimeMillis()` (ModificarOrigenDestino, GrabarTraspasos, ModificarPortafolioTraspaso, GrabarContratoTraspasoSAAPV): those values are masked as `<TS>`
  (`"enmascarar"` per table column, per output/trace key) on BOTH sides (`Dump.TIMESTAMP`: `yyyy-MM[-dd[ HH:mm:ss[.f]]]`). `PLA.FechaSistema` is the fixed `2025-04-01` of `seed/config.json`. Goldens carry no run-day literal
  (checked by `FamiliaBSelfCheckTest`).
- Identity hash codes (`@6d3af739`) and the JDK helpful NullPointerException text are normalised (`Dump.sinHash`) on both sides.
- Sequences: the oracle `Utils.getSecuencia` returns `firstValue, firstValue+1, ...` per name from `case.json "secuencias"` (default 1); SQL `NEXTVAL` inside a statement uses the real H2 sequence of the schema (CrearOrdenTraspaso,
  Crear_PortafolioContratoSAAPV): the two counters are independent here, as they are two reads of the same HANA sequence in production.
- `MensajeSalida.tipo` of a scripted collaborator answer is interned (`Hooks.internarTipos`): the legacy counts errors with `tipo == "ERROR"`, which only works for the literal strings the real in-process services create.
- No collaborator of family B writes a file; `AlmacenArchivosDeCaso` fails the case if the modern code uses the port.

## Decisions needed from a human

1. CrearTraspaso / GrabarContratoTraspasoSAAPV: keep the legacy behaviour (always an error / always an SQLException) or fix the INSERT parameter set in the migration? The tests pin the legacy behaviour.
2. The exception contract: the golden pins the exception CLASS NAME (`SQLException`, `NullPointerException`, `IndexOutOfBoundsException`, ...). A typed Spring implementation will throw other types (e.g. `DataAccessException`): decide whether to
   translate them to the legacy names or to relax the comparison for those cases.
3. Reference comparisons (`==` on `Long`/`String`) in CrearTraspasoTesoreria and IngresoRecaudacionTraspaso: port the value semantics the code was meant to have, or the cache-dependent behaviour recorded here?
4. `CalculoMontosDesinversion`: the ROUND_* indicators and the UF branch are dead in the legacy; confirm they are to be dropped (the cases pin the failure).
5. Table rows that depend on the real clock (`PeriodoInicio/PeriodoTermino`, `FechaModificacion`): confirm the modern code may take them from the `Reloj` port (the masks make the comparison independent of the value).
6. Recaudacion paths: the legacy reports a failed reconciliation as an OK-typed message with code `ERROR`, ignores the Tesoreria errors of the deposit, reuses one `MensajeSalida` (the reconciliation message is
   overwritten by the DIS error) and answers `REAPERTURAR_TRASPASO_OK` for a recaudacion that did not reconcile (cases 303, 307-308, 313, 343). Keep them (the goldens pin them) or report them as errors in the migration?
7. `IngresoRecaudacionTraspaso` calls `con.rollback()` itself when one of several traspasos fails and reverts the ones that succeeded (326): the modern use case must roll back the whole transaction of the call at that point,
   not only its own statements; confirm that this is the intended contract.
8. The three recaudacion views (`ConsultarRecaudadoDistribuido`, `ConsultarGestionContratosSAAPV`, `ConsultarDetalleTraspasosAPV`) are seeded rows here: the real HANA view definitions (or a sample of their rows for a traspaso)
   are needed to prove that the modern repository reads the same data (the DIS vs CON outcome of 340 / 341 depends on them).
